# CI-3 · Caché de descargas y reparto de Intel

Base `f2e3d7aa826c7d797261845373ef52a7ade111da`. El job Intel `csv-package` pasa a dos trabajos independientes, `csv` y `package`. El primero mantiene las E2E rápidas de CSV y toda la fase serial. El segundo instala dependencias, genera avisos de licencias, construye y ejecuta los mismos diez specs sobre la aplicación empaquetada. `shell-md` conserva tipos, unitarias, el experimento de archivos grandes y las E2E rápidas de Shell/Markdown. Los jobs Intel conservan sus 90 minutos y se ejecutan en push a `main` y en la nocturna. Gate y Release candidate conservan sus reglas.

## ADR 0021

1. **Herramienta existente.** `actions/cache` conserva archivos descargados, la matriz de GitHub Actions ejecuta las partes en paralelo y electron-builder admite las sumas oficiales del ZIP que ya trae el paquete `electron`.
2. **Skill reutilizada.** Ponytail limita el reparto a la matriz y a las condiciones de los pasos existentes. TDD comprueba las identidades completas que enumera Playwright y la lista original de specs empaquetados.
3. **Integración.** La caché de Electron restaura su ubicación nativa. La de herramientas de electron-builder usa `ELECTRON_BUILDER_CACHE` y solo participa en los jobs que empaquetan. Ambas claves incluyen sistema, arquitectura y hash de `package-lock.json`.
4. **Madurez, seguridad y licencia.** Se usa la acción oficial MIT de GitHub, fijada al [commit de v5.0.5](https://github.com/actions/cache/releases/tag/v5.0.5), con los permisos de lectura existentes. Las claves exactas evitan reusar entradas de otro lockfile. Electron y electron-builder conservan la verificación SHA-256. La caché contiene descargas, sin credenciales, fuentes ni `node_modules`.
5. **Mantenimiento.** Dos claves de caché independientes y una entrada adicional en cada matriz Intel. La separación permite que los jobs de desarrollo repueblen el ZIP sin guardar una entrada parcial de las herramientas de empaquetado.
6. **Pegamento mínimo.** Dos pasos de caché, la selección de la parte y una llamada corta a `electron-builder.build({dir: true})` con las sumas locales para evitar la descarga de `SHASUMS256.txt` al verificar un ZIP de caché. No se añade ninguna dependencia npm.
7. **Valor del código propio.** Las pruebas conservan el reparto y la cobertura de FreyaLab. La acción gestiona el almacenamiento y electron-builder realiza el empaquetado y la verificación.

## Descargas y verificación local

En el [job Windows 129022835804](https://github.com/ruzer/freyalab/actions/runs/42568131274/job/129022835804), electron-builder registró la descarga de Electron al 100 % y después un HTTP 504. El registro no identifica qué URL devolvió el error. La versión 26.15.3 consulta `SHASUMS256.txt` incluso al encontrar el ZIP, salvo que se le pasen las sumas. CI-3 usa las sumas que trae Electron 44.9.2 y conserva la verificación local del ZIP. Un caché frío, vencido o eliminado todavía necesita descargar los archivos ausentes.

- Rojo sobre `f2e3d7a`. Fallaron los tres casos de `tests/ci-int.test.ts` al no encontrar el reparto, el build independiente ni las cachés.
- Verde. `npm test -- tests/ci-int.test.ts tests/ci-areas.test.ts` aprobó 54 pruebas. El reparto comprueba el multiconjunto de proyecto, archivo, suites y título de Playwright. Los diez specs de la aplicación empaquetada conservan los comandos originales de prueba en Linux y escritorio.
- En macOS Apple silicon, `npm run licenses` y `npm run build` terminaron bien. El comando `build({dir: true})` del workflow produjo `release/mac-arm64/FreyaLab.app` con las descargas ya almacenadas. El registro `DEBUG=@electron/get:*` mostró un acierto del ZIP y ninguna consulta a `SHASUMS256.txt`. Con una ruta de builder vacía, el empaquetador sí pidió `icons-bundle.tar.gz`; al colocar esa descarga en la ruta cacheada, el empaquetado terminó sin red. Esta prueba local no mide restauración por GitHub Actions.
